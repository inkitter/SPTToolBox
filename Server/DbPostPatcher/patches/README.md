# Patch file format

Each `*.json` under `patches/` is one patch document. A filename starting with `_` is
reference-only (never a real patch to enable) and is excluded from the `available` list the
engine writes into `patches.enabled.json` - see `_example-append-vs-overwrite.json`.

```json
{
  "table": "items",
  "id": "<mongo id, or 'AccountType.side' for profileTemplates>",
  "description": "human note, not used by the engine",
  "ops": [
    { "op": "replace", "path": "/_props/medUseTime", "value": 1 }
  ]
}
```

`ops` is standard RFC 6902 JSON Patch, applied against the JSON serialization of the single
object named by `table`+`id` (not the whole database) - so a patch only ever touches the exact
fields it lists, no matter what else changes in that object's shape upstream.

- `path` is a JSON Pointer (RFC 6901): `/` separated, array indices are plain numbers
  (`/_props/Grids/0/_props/cellsH`), the literal `-` means "end of array".
- `op: "replace"` - the field/index must already exist. Overwrites just that value.
  Use this for "I know this field exists today and I'm intentionally changing it" -
  it fails loudly (the engine logs it and skips just that op, never crashes the server) if
  the field disappears in a future SPT update, which is the point: silent no-ops on a
  moved/renamed field are worse than a visible warning. This isn't hypothetical - it's
  exactly what caught a real bug while first testing this engine, see NOTES.md #7.
- `op: "add"` - creates the field if missing, or **overwrites** it if present (for object
  members). For an array index, it **inserts** without disturbing other elements; `/.../Filter/-`
  appends one entry to the end of an existing array.
- `op: "remove"` - deletes a field or array element.

## Overwrite vs append - which one do I want?

- `gamma-container.json` / `sicc.json` replace the *entire* `Filter` array with a single
  item type on purpose - the intent is "only this item may go in here", so wiping the rest
  of the original list is correct, not a bug.
- `_example-append-vs-overwrite.json` (reference only, not enabled) shows the other case:
  adding one entry to an existing `Filter` array via `add` + `/-` while leaving every other
  allowed item type untouched. Use this shape whenever the intent is "also allow X", not
  "only allow X".

This is the split that was easy to get wrong in `patch.ts` - a bare `=` assignment in
TypeScript always overwrites, so "add this one ammo type" and "restrict to only this ammo
type" looked identical in code even though they mean opposite things. JSON Patch forces you
to say which one you meant (`add` vs `replace`) at each field.

## Enabling patches

All files here are inert until listed in `patches.enabled.json`'s `enabled` array (gitignored,
machine-local - copy `patches.enabled.json.example` to start, or just build once and the engine
creates it). No rebuild needed to change which patches run, just edit the list and restart the
server.

`patches.enabled.json`'s `available` array is regenerated by the engine on every boot from
whatever's actually in `patches/` right now, so the deployed file always shows every patch you
could turn on, not just the ones already enabled - don't hand-edit `available`, only `enabled`.
